# W3 讲义 · 上下文是寄存器，不是硬盘

> 配合 `w3-context/` 使用。先读这份，再跑 `run_compare.py --dry-run`，最后才花 token。
> **这是八周里唯一不能跳的一周**：后面 W4 的返回裁剪、W5 的上下文增量、W6 的状态外置、
> W8 的渐进披露，全部建立在这周的账单上。

---

## 0. 先把账摆出来（不用花一分钱）

在 `w3-context/` 里跑：

```bash
python3 run_compare.py --dry-run
```

我这边跑出来的数（你的会略有出入，量级一致）：

| 策略 | 5 章语料的材料量 | 估算 token |
|---|---|---|
| A 全文塞入 | 102,973 字 | **46,241** |
| B 关键词检索 top-3（整节） | 3,045–9,510 字 | **1,703–4,892** |
| C 检索 + 抽取式压缩 | 1,038–1,133 字 | **554–616** |

再把范围换成全量（`--scope all`）：**约 27.5 万字，12.4 万 token**。

这就是 W3 的全部张力：**同一批问题，同一个模型，价格差 80 倍**。而 DeepSeek 的
上下文窗口是 64k —— 全量方案的 A 根本发不出去。这不是"优化"，这是"能不能做"。

## 1. 为什么"全塞进去"是最贵的默认选项

三个原因叠在一起，缺一个都不致命，凑齐了就是灾难：

1. **无状态**：W1 讲过，服务端不记得上一句。每一轮都要把整个历史重发，**重复付费**。
2. **按 token 计费**：输入便宜但不是免费，5 万 token 的输入乘以每天几十次调用，
   账单会以你意想不到的速度增长。
3. **注意力有限**：窗口 64k 不等于 64k 都"看得见"。中段信息被忽略是稳定复现的现象
   （lost in the middle），把材料堆满只会让关键那句更难被找到。

一句话：**上下文是寄存器——容量有限、每轮重新装载、装得越多越慢，不是硬盘。**

---

## 2. 四层分层：混在一起写，一定崩

| 层 | 内容 | 生命周期 | 放哪 |
|---|---|---|---|
| **常驻** | 角色、输出契约、工具定义 | 整个会话不变 | system，最前面 |
| **任务态** | 当前目标、已完成步骤、待办 | 随任务推进变 | 结构化状态（W6 会做） |
| **按需** | 检索结果、文件片段 | 用完即弃 | 紧挨着当前问题 |
| **易失** | 工具原始输出、日志 | 一次性的 | 裁剪后再进，原文落盘 |

判据很简单：**下一轮还会用到吗？** 会 → 往上提一层；不会 → 留在最底下，别升级。

大部分人写崩，是把"易失"层的东西直接 `cat` 进 messages，然后它变成了常驻的负担。

---

## 3. 前缀缓存：省钱的物理机制

服务商把**相同前缀**的 KV 计算结果缓存起来，下次命中就跳过重算。所以：

- **前缀一字不差才命中**。改一个字符，整段缓存失效。
- **稳定的放前面，变动的放最后**。这是唯一有效的排布原则。
- **时间戳是毒药**。system 里写 `当前时间：2026-11-05 14:23:01`，等于每轮都换一个新前缀，
  缓存命中率归零。这个错误极其常见，因为它"看起来很专业"。

`cache_probe.py` 就是让你亲手看一次：

```bash
python3 cache_probe.py                  # 稳定前缀，第 2 次应该便宜
python3 cache_probe.py --timestamp      # 塞了时间戳，第 2 次白搭
```

不同服务商的字段名不一样（DeepSeek 是 `prompt_cache_hit_tokens`，OpenAI 是
`prompt_tokens_details.cached_tokens`）。脚本不猜字段，把 usage 原样打出来——**你自己认**，
这个"认字段"的动作比背结论有用。

> 为什么要现在做这件事：W4 你要写 MCP server，工具定义会常驻在 system 里；
> W8 你要写 skill，frontmatter 也常驻。**凡是常驻的东西，都是"前缀"，都受这条规则支配。**

## 4. lost in the middle

长上下文里，开头和结尾的信息被利用得最好，中段最容易被忽略。

这条对你有两个直接后果：

1. **关键约束放头尾**。输出契约写在 system 开头，或者紧贴在 user 问题后面。
2. **不要指望"我塞进去了它就会看到"**。W2 的负例之所以有效，正是因为它贴在末尾。

验证方法很土但有效：把一条关键约束埋进 5 万字材料的正中间，看模型还遵不遵守。
`run_compare.py --scope all` 跑 A 就是天然的中段实验。

## 5. 工具输出是第一大成本

一个 `cat` 5000 行日志塞进上下文，比你想象中贵得多；更糟的是它**污染**了后面的推理。

所以 W4 的 `search_notes` 必须返回"3 段 × 200 字 + 文件路径 + 行号"，而不是全文。
这不是洁癖，是这周算出来的：

| 返回方式 | token | 后果 |
|---|---|---|
| 整节返回（1500 字） | ~700 | 一次工具调用吃掉一次问答的预算 |
| 片段 + 定位（200 字×3） | ~400 | 模型还能自己决定要不要再读 |

注意第二行不是纯省钱：**给了行号，模型才有"再读一段"的能力**。裁剪必须和定位一起给，
只裁剪不给定位，等于把书合上了。

## 6. 检索 vs 直接塞：那条 30% 的线

一个足够好的经验法则：

- 语料 **小于窗口的 30%**，且问题是**全局性**的（"总结一下这门课"）→ **直接塞**
- 语料大，或问题需要**精确命中**（"4.6 节的正规方程"）→ **再检索**

为什么不是"能检索就检索"？因为检索有**召回损失**：正确答案所在的那一节没被排进 top-3，
你就从"贵但答对"变成"便宜但答错"。**答错的成本远高于多花的钱。**

本周的数据会给你一个具体数字：如果 B 在 5 题上丢了 2 题，那省下的 90% token 值不值？

## 7. 压缩丢的是什么

| 方式 | 成本 | 丢什么 |
|---|---|---|
| 抽取式（当前 C 的实现） | 0 额外调用 | 丢限定条件。它只留"和问题高相关"的句子，而限定条件往往不含关键词 |
| 生成式（TODO） | 多一次调用 | 丢细节、可能引入幻觉，但更连贯 |

C 的实现里有一行值得注意的兜底：

```python
if len(out) > max_chars * 1.4:
    out = out[:max_chars]
```

**硬截断会切断句子。** 这类小事故在真实系统里天天发生，而且不会报错——它只会让你
的答案莫名其妙地缺一半。跑完 C 之后，去 `runs/*.jsonl` 里读几条 `material`，
看看有没有被切在句子中间。

## 8. 拐点：什么时候该换策略

不用做曲线拟合，线性外推就够：

```
A 的 token ≈ 语料总字数 × 0.45
B 的 token ≈ k × 单节平均字数 × 0.45
C 的 token ≈ 压缩预算 × 0.45 + 检索开销
```

所以：

- 语料 5 章（10 万字）→ A 约 4.6 万 token，**贵但能跑**
- 语料全量（27.5 万字）→ A 约 12.4 万 token，**超过 64k 窗口，跑不了**
- 结论：**窗口大小决定 A 的生死线，价格决定 B/C 谁更划算**

把这条写进 `report.template.md` 的拐点表，用你的实测数字填。

## 9. 和你已有能力的对照

| 你已经会的 | W3 里的对应物 |
|---|---|
| 寄存器 vs 内存 vs 磁盘 | 常驻 / 按需 / 易失 三层，容量与成本依次上升 |
| cache locality | 前缀缓存：命中靠"上次算过且没变"，跟你优化循环顺序是同一个直觉 |
| 洛谷的内存限制 | 上下文窗口：超了就是 RE，不是"慢一点" |
| 分布式里的重传成本 | 无状态接口：每轮把历史重发一遍 |

最后一条最关键：**你会本能地关心"这次传输带了多少数据"，只是还没把这个直觉用到
messages 数组上。** 本周就是把这根弦接上。

## 10. 验收怎么读

- 三套策略的 token 差异**能量级化**（不是 10% 的差别，是 10 倍的差别）
- 你能说出**在你的语料规模下**哪套最优、为什么、拐点在哪
- 你能说出 W4 的 `search_notes` 该返回多少字、什么格式、为什么必须带行号
- `cache_probe.py` 的两组数据你亲手看过，能解释"为什么时间戳会毁掉缓存"

做不到第 4 条就等于没做这周：W4–W8 所有"常驻上下文"的设计都靠它。
