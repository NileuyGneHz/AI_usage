## 一、先定位：你缺的不是 ML，是"把模型当可编程组件"的工程直觉

你已经有的（这些在 LLM 应用里是**超配**，不是勉强够用）：

| 已有能力 | 在这件事上的直接价值 |
|---|---|
| C++ / 系统编程 | 读 SDK 与协议实现不费力；写确定性工具、理解并发与超时 |
| ROS 2 | MCP 的 client/server、生命周期、能力协商，你在 ROS 里都见过同类结构；"消息没到"的排查直觉可直接迁移 |
| 数学基础 | embedding、余弦相似度、logprob、温度采样，看一眼公式就懂，不用等教程喂 |
| 竞赛工程经验 | 你知道"能跑"和"能交付"差多少，这个判断力比知识点更稀缺 |
| Ng 机器学习课程 | 应用层不需要反向传播，你现有的深度足够 |

要补的是三件事，按摩擦大小排：

1. **作者经验：从零写一个工具、一个 skill。**（最缺，也最容易补）在这两个形态上你是**纯粹的消费者**——用过别人配好的 MCP，装着 AI 代写的 skill，但没有过一次"我写的函数被模型当成工具调起来"或"我写的判断被 agent 照着执行"的经历。难点不在技术，在破除"这东西很神秘"的心理门槛，所以 W0 用一个晚上一次性解决。
2. **Python 工程化** —— LLM 生态的母语。类型标注、`venv`、`pytest`、`asyncio`、`pyproject.toml`。你 C++ 熟练、Python 有基础，这会成为整个计划里最主要的摩擦点。
3. **评测习惯** —— 玩具与工程的分水岭。没有评测集，调 prompt 就是凭感觉做梯度下降。

**关于 `~/.workbuddy/skills/` 那批 skill（2026-11-05 现算 21 个），价值要重新估**：既然你一个都没写过，它们就都是 AI 代写的产物，不是你的能力证明。

| 视角 | 结论 |
|---|---|
| 当能力证据 | 不成立。作者是你雇的模型，你是使用者 |
| 当阅读样本 | 有价值。它们代表了一个称职作者的产出形态，可以反读 |
| 当资产 | **实质是负债**。21 个文件、共 3,488 行、19 个没有脚本、常驻约 2,684 token/次请求，而你没有能力判断其中哪一条已经过期或写错 |

所以 W8 不是"重构你的作品"，而是"**接管一批你继承的文件**"——这才是更真实、也更常见的工程处境。而接管的前提，是你先亲手写过一次。

## 二、能力栈全景

六个层次，从"看见裸的请求"到"封装成别人能用的东西"。**顺序不能跳**：跳过 L0 直接学框架，你会永远不知道框架替你做了什么。

```
W0 破冰      各写一个最小件：一个 tool + 一个 skill         一个晚上
L0 裸调用      messages 数组 / 流式 / token 计量            W1
L1 Prompt     用 schema 定输出契约，不用形容词提要求        W2
L2 Context    分层、裁剪、前缀稳定吃缓存                    W3
L3 Tools/MCP  JSON-RPC 上的三大原语，把系统能力接给模型      W4–W5
L4 Agent      while 循环 + 终止条件 + 状态外置 + 评测        W6–W7
L5 封装       渐进披露：机制写成手册，确定性写成脚本          W8
```

三个阶段的性质不同：**W1–W3 是输入侧**（控制模型看到什么），**W4–W5 是能力侧**（控制模型能做什么），**W6–W8 是封装侧**（控制这套东西能不能被别人复用）。

换个说法，这条路线是三重身份的切换：

| 身份 | 你在做什么 | 对应 |
|---|---|---|
| **使用者** | 用别人配好的东西，只会描述需求 | 你现在的状态，已经很熟 |
| **作者** | 自己写出一个工具、一个 skill，知道每一行为什么存在 | W0–W5，完全空白 |
| **设计者** | 判断该用哪种形态、怎么验证它没坏、能不能交给别人 | W6–W8 |

大多数人卡在第一重就以为自己在做第二重——"我让 AI 写了个 skill" 读起来像"我写了个 skill"。这两件事的差别，只在你亲手调试过一次之后才显形。

### W0 · 破冰：一个晚上，两个最小件

**目标**：在碰任何真代码之前，先亲手写一个 MCP tool 和一个 skill，各 30 分钟，都不许加功能。

**为什么把这件事提到最前**：这两样你从没写过，而八周里后面所有内容都建立在"我做过"的手感上。门槛不在技术——`mcp_demo.py` 只有 43 行，`SKILL.md` 只有 54 行——而在"我是不是根本没资格碰这东西"的心理预设上。一天就能证伪。

**具体步骤在 `w0-icebreak/README.md`，骨架已就绪**：

```
w0-icebreak/
├── README.md              # 30 分钟 × 2 的操作步骤
├── mcp_demo.py            # 43 行，一个 tool + 一个 resource
├── raw_rpc.py             # 60 行最小 client，把 JSON-RPC 每一行打出来
├── requirements.txt       # 锁 mcp<3，避开版本坑
└── skill-template/        # 一个完整的 skill 例子，抄改即可
    └── SKILL.md
```

```bash

```

顺带说一句：那个示例是**实测跑通过的**（mcp 2.3.0）。我第一版按 1.x 写法写了 `FastMCP`，装上新版直接 ImportError——所以破冰里特意留了"撞一次版本墙"这一步，让你亲手体验"教程没写版本"这件事有多常见。W8 那道"你怎么判断一个 skill 过期了"的题，考的是同一种能力。

**验收（四条都必须过）**
- 撞过一次版本墙，能说出为什么不能直接抄教程里的 import
- 能在 `tools/list` 的返回里指出：哪个字段决定"调不调"，哪个字段决定"怎么调"
- `~/.workbuddy/skills/` 下有一个你自己写的 skill，且被**成功自动召回**过一次

最后一条最容易含糊过去：`tool` 由模型决定何时调用，`resource` 由 client 决定何时注入。**这个区别决定了你后面所有封装形态的选择**（W8 的三选一判据就是从这来的）。

第一次就写"有用的"工具会失败。选最蠢的例子（统计行数），把注意力全放在"看报文"上。W0 的产出不是工具，是理解。

### W1 · 裸调用：先看见 HTTP 里的东西

**目标**：不借助任何框架，让一次请求和一次响应完全透明。

**必须搞懂**
- `messages` 是数组，`system` / `user` / `assistant` / `tool` 四种角色各自的语义与优先级
- `usage` 字段：input / output token 分别计费，缓存命中单独计价
- `temperature`、`top_p`、`max_tokens`、`stop` 的真实作用（不要背定义，做实验：固定 prompt，扫 temperature 看输出分布）
- 流式（`stream=True`）与增量解析；为什么流式在 agent 里是必需品（用户等待感、可中断）
- 结构化输出：`response_format` / JSON Schema 约束 vs "请你输出 JSON"

**交付物**
`w1-bare-api/NOTES.md`（目录已就绪，含三个脚本，见下）。

`w1-bare-api/` 已备好可跑骨架，三条路任选，**没有 API key 也能把逻辑全部跑通**：

| 文件 | 角色 | 依赖 |
|---|---|---|
| `raw_http.py` | 手写 HTTP + 手工解析 SSE，什么都不藏 | 纯标准库 |
| `hello_llm.py` | 同一任务用官方 SDK 再写一遍，用来对照"它藏了什么" | `openai` |
| `mock_server.py` | 假的 OpenAI 兼容服务，零成本验证客户端逻辑 | 纯标准库 |

**先读 `w1-bare-api/LECTURE.md`**（概念拆解 + W0 笔记订正 + 与 C++ / ROS 2 / 洛谷刷题的对照），再 `python3 raw_http.py --dry-run` 看请求体（不联网），然后起 mock 跑通流式，最后才配真 key。具体步骤和五个必做实验在 `w1-bare-api/README.md`。

**验收**
- 能画出这张图：你的字符串 → HTTP body → 模型 → HTTP response → 你的对象，每一段里有什么
- 能回答：为什么"请输出 JSON"不可靠，而 schema 约束可靠？两者失败时的表现有什么区别？
- 能说出：同一段 prompt 第二次调用为什么更便宜

**坑**
用第三方 SDK 时先 `curl` 一次裸请求。SDK 会替你补默认参数（system prompt、重试、超时），看不见就会在别处踩。

### W2 · Prompt：契约化，不是修辞化

**目标**：把 prompt 从"写作"变成"接口定义"。

**必须搞懂**
- 五个槽位：角色 / 任务 / 输入边界 / 输出契约 / 失败处理（"信息不足时输出 `insufficient`，不要猜"）
- **指令优先级**：system > developer > user；工具返回的内容是**不可信输入**，不能当指令执行（这是 prompt injection 的入口，W5 会实战）
- few-shot 的正确用途：定**格式与边界**，不是教能力。新模型上示例的边际收益在下降，但用来钉住"什么算不合格答案"仍然有效
- 负例比正例更省 token："不要总结成段落"比三个段落示例更有效
- prompt 要进 git，要有版本号与变更记录

**交付物**
`w2-prompt/`：一个"ML 概念出题器"——输入 `ml-course/Coursera-ML-AndrewNg-Notes/markdown/` 里某一章，输出 3 道题 + 答案 + 考查点，JSON 结构化。
同一任务写 **v1（自然语言描述）/ v2（槽位化）/ v3（schema + 负例）**三版，用 10 个固定输入跑一遍，记录：格式合规率、内容可用率、平均 token。

**验收**
v3 的格式合规率 10/10，且总 token 不高于 v1 的 1.5 倍。做不到就继续改，这一周的功夫全在这里。

**坑**
不要在 prompt 里写"你是一个资深的机器学习专家"这种角色扮演就以为提升了质量。角色设定对**语气**有效，对**正确率**基本无效。真正起作用的是约束与示例的精确度。

### W3 · Context：把它当寄存器，不是硬盘

**目标**：建立"上下文预算"意识。这一周决定你后面所有东西的成本与稳定性。

**必须搞懂**
- **分层**：常驻（规则/契约）、任务态（当前目标、已完成步骤）、按需（检索结果、文件内容）、易失（工具原始输出）。四层混在一起写，一定崩
- **前缀稳定 = 缓存命中**：prompt 前缀（system + 工具定义）只要变一个字符，KV cache 全失效，成本和延迟差数倍。所以：**变动的内容永远放最后，稳定的放最前**，且不要在 system 里塞时间戳
- **lost in the middle**：长上下文里中段信息最容易被忽略，关键约束放头尾
- **工具输出是第一大成本来源**：`cat` 一个 5000 行日志塞进上下文，比你想的贵得多。先裁剪、先摘要、先给路径与行号让人（或模型）按需再读
- **检索 vs 直接塞**：语料小于窗口 30% 且查询是全局性的 → 直接塞，别上 RAG；语料大或需要精确命中 → 再检索。检索的召回损失常常大于省下的钱

**交付物**
`w3-context/`：同一个任务（"根据笔记回答 5 个问题"）三套策略对比——
A 全文塞入 / B 关键词检索 top-k / C 检索 + 摘要压缩。
输出一张表：token 消耗、正确率（人工判 5 题）、首次响应延迟。

**验收**
能说清楚在你的语料规模下哪套最优、为什么，以及拐点大概在哪（语料涨到多少该换策略）。

**坑**
"上下文窗口大"不等于"可以不管"。窗口 200k 但注意力有效范围远小于此，且成本随长度线性涨。

### W4 · MCP 上：协议与第一个 server

**目标**：不看教程，直接读 spec 写一个能用的 server。

**必须搞懂**
- 本质：**JSON-RPC 2.0**。一个 `tools/call` 就是一次带 `id` 的请求/响应，没有魔法
- 三大原语与**控制权归属**（这是最容易记混的地方）：
  - `tools` —— 模型决定何时调用（model-controlled），有副作用
  - `resources` —— 应用/Host 决定何时注入（application-controlled），只读上下文
  - `prompts` —— 用户显式触发（user-controlled），本质是斜杠命令模板
- 生命周期：`initialize`（能力协商，双方声明支持什么）→ `initialized` 通知 → 正常调用
- 传输：**stdio**（本地子进程，最简单，先做这个）与 **Streamable HTTP**（远程；2025-03 版规范已用它取代早期的 HTTP+SSE）
- `inputSchema` 是标准 **JSON Schema**，不是自定义描述

**为什么对你简单**：MCP 的 client/server、能力协商、生命周期，和 ROS 2 的节点/服务/参数声明是同一类问题。你已经有的分布式系统直觉可以直接搬过来，只需要替换名词。

**交付物**
`w4-mcp-stdio/`：`ml-notes-mcp` server，至少 3 个 tool + 1 个 resource：
- `search_notes(query, chapter?)` → 返回命中片段 + 文件路径 + 行号
- `read_section(path, start_line, end_line)` → 按行读，不整篇返回
- `list_chapters()` → 章节清单
- resource：`notes://index` —— 全部笔记的目录树
语料用你现成的 `ml-course/.../markdown/*.md`（15 个文件、125 个小节，规模刚好）。

**验收**
用 MCP Inspector 或任意 client 手工发 `tools/list`、`tools/call`，看到完整 JSON-RPC 报文。**先手工跑通报文，再接 LLM**。

**坑**
不要把 `search_notes` 写成返回全文。返回 3 段、每段 200 字以内 + 精确定位，比返回 5000 字有用得多（回到 W3 的结论）。

### W5 · MCP 下：工程化，接进真实 client

**目标**：从"能跑"到"敢给别人用"。

**必须搞懂**
- **工具描述就是 prompt**：`description` 决定调用准确率。写清楚"什么时候该用、什么时候不该用、返回什么"，比写清楚参数更重要
- schema 要**收紧**：`enum` 比自由字符串好，`required` 要真的必填。宽松 schema 让模型自由发挥，错误率上升
- **错误要可读**：模型靠错误信息自我修正。返回 `"Error: file not found"` 它会换路径；返回堆栈它会放弃
- annotations：`readOnlyHint` / `destructiveHint` / `idempotentHint`。有副作用的工具必须标记，这是 Host 决定要不要弹确认的依据
- 大结果**分页**；有副作用的操作**幂等**（重试不该写两次）
- 安全边界：工具能碰什么、不能碰什么，在代码里硬约束，不要写在 description 里靠模型自觉

**交付物**
`w5-mcp-http/`：
1. 把 W4 的 server 增加 Streamable HTTP 传输
2. 在 WorkBuddy 里注册（`~/.workbuddy/mcp.json`），实测 10 个真实提问
3. 记录：调用成功率、误调用次数、平均上下文增量

**验收**
问"线性回归的正规方程是什么"，agent 自动调用 `search_notes`，答案带**文件路径 + 行号**；10 问里调用正确 ≥ 8 次。达不到就回去改 description 和 schema——这一周的产出质量几乎全由这两项决定。

**坑**
`description` 里堆功能清单（"可以搜索、读取、列目录、统计……"）会让模型分不清何时用哪个。一个 tool 一件事。

### W6 · Agent：手写循环，不许用框架

**目标**：亲手写一遍那个循环。写完你就再也不会被框架唬住。

**必须搞懂**
- 本质就这么多：
  ```
  while not done and steps < MAX:
      resp = llm(messages, tools)
      if resp.tool_calls: 执行 → 结果 append 进 messages
      else: done
  ```
- **终止条件**要三重：模型说完了 / 达到最大步数 / 超出预算（token 或钱）。缺一个都会出现"跑到天亮"
- **状态外置**：把计划、已完成步骤、中间结论写在结构化状态里，而不是靠对话历史隐式携带。这样才可中断、可恢复、可调试
- **子 agent 的真正价值是上下文隔离**，不是"分工"。把一个会读 30 个文件的子任务丢给子 agent，它烧完自己的上下文后只回一句结论——主上下文干干净净
- ReAct 的脆弱点：错误会累积。缓解靠"每步可验证 + 结构化状态 + 可回滚"，不是靠更长的 prompt

**交付物**
`w6-agent-loop/`：≤ 120 行（不含工具实现）的 agent，完成一个多步任务：
> 读某一章笔记 → 找 2 个核心公式 → 生成 3 道题 → 自查答案与笔记是否一致 → 输出 markdown

必须带 `max_steps` 与 token 预算，超限要有明确退出原因。

**验收**
故意让它做一件不可能的事（"找第 99 章"），观察它是否在有限步内**优雅失败**而不是空转。这一步能过，说明你的终止逻辑是对的。

**坑**
不要在这一周引入任何 agent 框架。框架的价值在你写过一遍之后才会显现——那时你才知道该用它的哪部分。

---

### W7 · 评测：把"感觉变好了"变成数字

**目标**：建立回归能力。这是整个计划里最不性感、最保值的一周。

**必须搞懂**
- **golden set**：20 条就够。每条包含输入、期望行为、判定方式
- 三层断言（从易到难）：
  1. 结果断言：最终答案包含关键事实
  2. 轨迹断言：**该调的 tool 调了没有、有没有多余步骤**（比结果断言更能暴露问题）
  3. 负例断言：该拒绝的时候拒绝了没有
- **trace**：每一步记 `step / tool / args / result_digest / tokens / latency`。出问题时你需要的是回放，不是重跑
- 回归：改 prompt / 改 description / 换模型，跑一遍评测集，对比通过率。**没有这一步，你的所有优化都是猜测**

**交付物**
`w7-eval/`：`evalset.jsonl`（20 条）+ `run_eval.py` + 一份对比报告（W6 版本 vs 改 description 后 vs 换小模型后）。

**验收**
能指着报告说："换小模型后通过率从 17/20 掉到 13/20，掉的是'需要多步推理'那 4 条，成本降 60%，我选择保留大模型。"——这就是工程判断。

**坑**
用 LLM 当裁判（LLM-as-judge）可以，但先人工标 20 条做校准。没校准的裁判只会给你一个看起来很专业的错误结论。

### W8 · 封装：从"写一个"到"接管一批"

**目标**：具备维护"不是自己写的资产"的能力。这比从零写更接近真实工程处境。

**必须先看的事实**：`~/.workbuddy/skills/` 那 21 个不是你写的（`w8-skill-pack/audit_skills.py` 可现算）。`rm-nav-dev-push-decision` 371 行、`docker-pull-stall-cn` 326 行、`ros2-topic-bridge-verify` 286 行——全部是"一次性全量进上下文"的单文件手册，里面的确定性步骤（编译检查、报文校验）也没抽成脚本。它们现在能用，只是因为写的那一刻模型是对的；**你并没有能力判断它们从什么时候开始错**。这一周就是补这个窟窿。

**必须搞懂三选一判据**
| 形态 | 什么时候用 | 你的例子 |
|---|---|---|
| **tool / MCP** | 确定性、需权限、要被模型主动调用 | `search_notes`、编译检查 |
| **skill** | 多步流程知识、判断规则、踩坑经验 | `bt4-loop-decorator-pitfalls` |
| **subagent** | 需要独立上下文、过程脏但结论干净 | "扫 30 个文件找断链" |

判据一句话：**能写成代码的写代码，只能写成判断的写手册，会污染主上下文的拆出去。**

**必须搞懂 skill 的结构**
- 渐进披露三层：frontmatter 的 `name` + `description`（常驻，永远在上下文里）→ `SKILL.md` 正文（命中才加载）→ `references/` + `scripts/`（正文点名才读）
- **`description` 决定召回率**，写法和 MCP 的 tool description 完全同理：写触发条件与症状，不写功能简介
- 手册里凡是"照这个命令敲"的段落，都该变成脚本；模型执行 10 行固定命令的可靠性，永远低于执行 1 个脚本

**三级任务，按顺序做，前一级不过不进入下一级**

**L1 · 读**（2 h）：挑两个极端样本对照——`nuedc-topic-research`（60 行，最短）与 `rm-nav-dev-push-decision`（371 行，最长）。各回答五问：
1. `description` 写的是症状还是功能？换成你会怎么写？
2. 正文里哪些是"照这个命令敲"？本该是脚本吗？
3. 哪些是长案例 / 参考资料？本该在 `references/` 吗？
4. 有没有过期信息（路径、版本、命令）？你**怎么**判断它过期了？
5. 如果它执行错了，你能从文件里定位到是哪一句指令导致的吗？

五问答完，"什么是好 skill"才算有了标尺。这一步不能跳——你对 skill 的全部认知目前来自这些文件的**结果**，不是它们的**设计**。

**L2 · 写**（4 h）：W0 那个 15 行的是玩具。这一级写真的：选一件你每周重复做、步骤 ≥5 的事，产出可用 skill。硬要求：正文 ≤120 行、至少 1 个确定性步骤抽成 `scripts/`、`description` 按 W0 练出的写法。在 5 个真实场景试，记录命中率与执行成功率。

**L3 · 改**（2 h）：挑 1 个 AI 写的 skill 做**受控改动**——只改 `description`，或只把长案例拆进 `references/`，一次只动一个变量，然后同样 5 个场景对比前后。目的是验证你能安全地修改一个你并不完全理解的文件的局部。

**加分项**：把 W4–W7 的产物打包成可分发的 agent（skill + MCP server + 评测集），让一个没参与的同学按 README 在 20 分钟内跑起来。

**验收**
- L1：五问在 `w8-skill-pack/review.md` 里都有具体答案，不接受"看起来还行"
- L2：5 个场景里被正确召回 ≥ 4 次
- L3：改动前后的数据都在，且你能指出差异来自哪一句
- 加分项：同学独立跑通，不需要你在旁边解释

## 五、反模式清单（贴在显示器上）

1. **先学框架再学原理**。LangChain / LlamaIndex 抽象层会掩盖你唯一需要理解的东西：一个 while 循环加一次 HTTP POST。
2. **用 RAG 解决"上下文太长"**。先算 token 账，语料小于窗口三成时检索通常是净亏损。
3. **用自然语言要求格式**。要 JSON 就用 schema，别写"请严格按 JSON 输出"然后祈祷。
4. **过早 multi-agent**。单 agent 评测集过 80% 再谈拆分。
5. **不做评测就调 prompt**。你在用感觉做梯度下降。
6. **skill 写成 300 行大散文**。渐进披露不是形式主义，是上下文成本。
7. **把工具返回值原样塞回上下文**。第一成本杀手，也是上下文污染的主要来源。
8. **相信模型的自述**。"我已经完成了"必须用工具结果验证，不能作为终止依据。
9. **把工具返回内容当指令**。那是不可信输入，prompt injection 就从这里进来。
10. **把 AI 代写的产物当成自己的能力**。它能写出来，不等于你能改、能判断它错在哪。作者身份只能靠亲手写一遍获得，没有别的路径。

## 附录一 · 它们到底是怎么被"调用"的

这是你目前最直接的困惑，现在就说清楚：**没有魔法，宿主程序在读文件、拼字符串、代理执行。**

**Skill 的加载链路**

1. 宿主启动时扫描 `~/.workbuddy/skills/*/SKILL.md`，**只读 frontmatter**
2. 把每个 skill 的 `name` + `description` 拼进 system prompt —— 这部分**常驻上下文**，所以描述越短越准越好，写长了是纯成本
3. 你提问 → 模型判断"要不要用某个 skill" → 决定读取该 `SKILL.md` 正文
4. 正文进上下文；正文里点名的 `scripts/` 才会被执行

于是三层各管一件事：**description 决定召回，正文决定执行，scripts 决定可靠性。**

**MCP 工具的调用链路**

1. 宿主按 `mcp.json` 启动你的 server 子进程（stdio），或用 HTTP 连上远程 server
2. `initialize` 协商能力 → `tools/list` 拿到每个工具的 `name` + `description` + `inputSchema`
3. 这些定义同样拼进 system prompt（**也是常驻**）
4. 模型输出 `tool_calls` → 宿主转成 `tools/call` 发给你的 server → 你的 Python 函数被执行
5. 返回值以 `tool` 角色消息回填进对话 → 模型继续

**两条链路结构完全一样**：把描述放进上下文 → 模型做决定 → 宿主代执行 → 结果回填。
差别只有一处：skill 回填的是**文字指令**（靠模型理解，有概率偏差），MCP 回填的是**函数返回值**（确定性的）。

这就是 W8 那个"三选一判据"的由来，不是背的，是从链路里推出来的。

## 附录二 · 你手上那份 PPT 的词汇，对应到哪一周

你已有的概念不是白学的，它们都能落到具体的一周。但有三处会被带偏，先说这个。

**要先纠正的三个偏差**

1. **"Context = MCP" 是那份材料里最误导的一句。** MCP 解决"模型能调什么"，上下文解决"模型看到什么"。后者更基础、更便宜、收益更大。你现在 90% 的坑会在上下文层，不在 MCP 层——这也是 W3 排在 MCP 之前的原因。
2. **Harness 不是起点，是终点。** "Harness 定义真理"成立的前提是：你已经有一个能跑、能反复跑的东西。你现在还没有，所以在拿到 20 条 golden set 之前，"断言测试床"只是一个词。评测排到 W7，就是这个原因。
3. **多 agent 金字塔对你现在是负收益。** Supervisor/Worker 解决的是"单上下文装不下"和"并行加速"。你连一个 agent 循环都没手写过，拆多 agent 只会让你同时调试两个黑箱。W6 先写单 agent，只用一个子 agent 体会"上下文隔离"这一个作用。

**映射表**

| PPT 里的说法 | 准确的含义 | 你会亲手做的对应物 | 周次 |
|---|---|---|---|
| MCP 万能总线，一次编写全生命周期复用 | 工具接入协议，不管上下文 | 写 server 并注册进 WorkBuddy | W0 / W4–W5 |
| Skills 标准能力包，SKILL.md 统一 | 流程知识，靠 description 召回 | 写一个被自动召回的 skill | W0 / W8 |
| 渐进式披露，正文 <200 行 | 上下文预算的分层策略 | 三层披露 + 前缀缓存实测 | W3 / W8 |
| Harness 断言测试床，定义真理 | 评测集 + 回归，不是框架 | 20 条 golden set + trace | W7 |
| 四层防线 L1–L4 | AGENTS.md / skill / 脚本 / hook 的取舍 | 判断某步骤该写成哪种形态 | W8 |
| Gateway 核心关卡 | 权限与副作用的边界 | annotations + 只读约束 | W5 |
| Context Drift / 代码拔河 / 熔断 | 长任务的失败累积与止损 | max_steps + 预算 + 状态外置 | W6 |
| Supervisor / Worker 金字塔 | 上下文隔离（不是分工） | 一个子 agent 烧完 30 个文件只回一句 | W6 |
| Vibe coding / 规格驱动 | 把意图变成可验证的契约 | prompt v1/v2/v3 对比 | W2 |
| RAG / 文案校验等业务例子 | 应用层选题 | —— | 八周后再看 |

那份材料的价值在于：它给你一套**名词**和一套**问题清单**（漂移、拔河、熔断）。你现在要做的是把每个名词背后变成一次亲手操作。名词你已经有了，缺的只是操作。
