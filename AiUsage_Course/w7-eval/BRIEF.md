# W7 · 评测与回归 — 任务卡

> 状态：骨架已升级为可跑脚手架（2026-11-05）
> 最不性感、最保值的一周。**没有评测集，调 prompt 就是凭感觉做梯度下降。**
> 入口顺序：`LECTURE.md`（为什么）→ `README.md`（怎么做）→ 本文件（交什么、怎么算过）。

## 目标

把「感觉变好了」变成数字。核心不是写测试框架，是建立**回归能力**：改任何东西之后，能跑一遍对比。

## 依赖

- W6 的 agent 与 `trace/`（轨迹断言直接读它）
- W2 的 `cases.jsonl`、W5 的 `questions.md`：真实提问是 golden set 最好的来源
- W1 实验 2 的结论：temperature=0 也不保证逐字相同，所以断言要判「包含关键事实」而不是字符串相等

三层断言（从易到难）：
1. **结果断言**：最终答案包含关键事实
2. **轨迹断言**：该调的 tool 调了没有、有没有多余步骤 ← 比结果断言更能暴露问题
3. **负例断言**：该拒绝的时候拒绝了没有

对比三组：W6 原版 vs 改 description 后 vs 换小模型后。

## 验收

能指着报告说：「换小模型后通过率从 17/20 掉到 13/20，掉的是『需要多步推理』那 4 条，成本降 60%，我选择保留大模型。」——这就是工程判断。

## 待定决策

1. **20 条从哪来**：全部新写，还是从 W2/W5 的真实提问转？**建议后者**，那些问题已经被真实使用过，不会偏袒当前实现。
2. **用不用 LLM-as-judge**：可以，但**先人工标 20 条做校准**。没校准的裁判只会给你一个看起来很专业的错误结论。
3. **断言粒度**：先做结果断言跑通，再补轨迹断言。负例断言最后加。
4. **跑几次**：单次结果有随机性。每个配置跑 3 次取通过率均值，还是只跑 1 次？W1 实验 2 已经告诉你答案了。
5. **trace 保留多久**：出问题时你需要的是回放，不是重跑。建议每次运行落一个文件，别覆盖。

## 可调整 / 压缩

W6 + W7 合并时，评测集压到 10 条、只做结果断言。**但「改 description 前后对比」不能砍**——这是整个计划里唯一一次把「优化」变成可验证动作的机会。

## 坑

- 别用字符串相等判答案，会全是假失败。
- 单次通过率不能下结论，模型有随机性。
- 断言失败时要能一眼看出是「结果错」还是「轨迹错」，两者修法完全不同。
