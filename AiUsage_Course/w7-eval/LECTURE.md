# W7 讲义 · 评测：把「感觉变好了」变成数字

> 配合 `w7-eval/` 使用。这是八周里最不性感、也最保值的一周。
> 前面所有周的经验，都会在这周变成可以复现的数字；没有这周，它们只是印象。

---

## 0. 一句话

评测不是"写测试框架"，是**建立回归能力**：改任何东西之后，你能在十分钟内知道
"变好了还是变坏了、坏在哪一层"。没有这个能力，你后面所有的"优化"都是猜测。

---

## 1. 20 条就够，但必须是"真问题"

| 做法 | 结果 |
|---|---|
| 新编 20 条 | 会不自觉地贴合你当前的实现 → 全绿，但没有信息量 |
| 从 W5 的真实提问转 10 条 + 自己补 10 条边界 | 会红几条，红的那些才是价值 |

每条只有三样东西：

```json
{"input": "用户会怎么问", "expect": "期望发生什么", "judge": "谁来判、怎么判"}
```

`judge` 现在写 `human`。别急着上 LLM——第 5 节讲为什么。

---

## 2. 三层断言，逐层加难

| 层 | 断言什么 | 抓什么 bug | 修在哪 |
|---|---|---|---|
| **结果** | 答案包含关键事实 | 编造、答非所问 | 检索 / 裁剪 / prompt |
| **轨迹** | 该调的调了没有、有没有多调、步数超没超 | **流程错**（最隐蔽） | description / schema |
| **负例** | 该拒的时候拒绝了没有、有没有动不该动的工具 | 越界、注入 | 工具权限 / 拒绝话术 |

为什么轨迹层最值钱：**一个答案正确但轨迹错误的系统，是运气好，不是工程对。**

例子：问"正规方程是什么"，它没检索、直接答对了——结果断言绿，轨迹断言红。
这次对是因为这个知识在模型权重里；换成"6.7 节的一对多策略"它就会编。**先看到红，才不会在
下一个问题上被坑。**

---

## 3. trace 与回放：为什么不能靠重跑

重跑有三个问题：

1. **随机性**：temperature=0 也不保证逐字相同（W1 实验 2），重跑可能换个错法
2. **成本**：20 条 × 3 次 × 每次十几步，钱和时间都不便宜
3. **不可复现**：改了 prompt 之后，旧版本的行为再也拿不回来了

所以 trace 必须**落盘且不覆盖**（W6 的 `trace/<run_id>.jsonl` 就是为这个设计的）。
`run_eval.py --replay <dir>` 只验轨迹层——因为 trace 里没有最终答案，
但"它调了什么"已经足够判一半的错。

> 一句话：**出问题时你要的是回放，不是重跑。**

---

## 4. 统计：通过率是数字，不是布尔

三条纪律：

1. **每配置跑 3 次**，报通过率均值。单次结果会被随机性骗（W1 已经证过）
2. **分层报**：结果 / 轨迹 / 负例分开，别只报一个总分——总分相同，修法可能完全不同
3. **记成本**：token 与步数一起进表。没有成本的"通过率提升"没有决策价值

计划里那个句式就是这三条的组合：

> 换小模型后通过率从 17/20 掉到 13/20，掉的是"需要多步推理"那 4 条，
> 成本降 60%，我选择保留大模型。

注意它同时说了**掉了哪类**和**省了多少**——这才是工程判断，不是分数比较。

---

## 5. LLM-as-judge：先用 20 条校准

让模型当裁判很诱人（省人力），但没校准的裁判会给你一个**看起来很专业的错误结论**。

最低校准流程：

1. 你人工判 20 条（半小时）
2. 让裁判判同样 20 条
3. 算一致率。**低于 85% 就别用**，或者只让它判"格式类"不判"事实类"
4. 把不一致的条目 id 记进报告——那些正是你的评分标准写得不够清楚的地方

## 6. 对比实验：一次只动一个变量

| 配置 | 改了什么 | 预期 |
|---|---|---|
| baseline | W6 原版 | 起点 |
| after_desc | 只改 description | 轨迹层变好，结果层不动 |
| small_model | 只换小模型 | 结果层掉，成本掉 |

三组跑完，你会得到一张 3×3 的表。**这张表就是"工程判断"的原材料**。

如果你一次改三样，得到的是一张漂亮的表和一个错误的归因——和 W2 的 v3 是同一个坑。

---

## 7. 失败分类：三种错，三种修法

| 失败 | 现象 | 修法 |
|---|---|---|
| 结果错 | 关键事实缺失 / 编造 | 检索召回、裁剪粒度、prompt 的输入边界 |
| 轨迹错 | 漏调、多调、步数超 | description 的"何时用/何时别用"、schema 收紧 |
| 负例失守 | 该拒没拒、动了只读工具 | 代码里的硬边界、拒绝话术 |

`run_eval.py` 的报告里这三列是分开的，别把它们合成一个总分。

---

## 8. 两个会让你自欺的陷阱

### 8.1 假绿

`must_include` 为空时，结果断言恒真——报告全绿，其实什么都没测。
`run_eval.py` 会在 `--dry-run` 时警告这一点。**看到警告就去补，别忽略。**

### 8.2 自证清白的 evalset

如果 20 条全是你照着当前实现想的，那它测的是"实现是否符合我的想象"，不是"系统好不好"。
两个解法：

- 一半条目来自**真实使用记录**（W5 的 `runs/*.jsonl`）
- 至少 3 条是**当前一定失败**的（比如"把 week2.md 整个读一遍"），它们用来标定天花板

## 9. 和你已有能力的对照

| 你已经会的 | W7 里的对应物 |
|---|---|
| 单元测试（断言 + 固定输入） | 结果断言 |
| 集成测试（流程正确性） | 轨迹断言 |
| 回归测试（改完跑一遍） | 三配置对比 |
| OJ 的测试点设计 | evalset：正例 + 边界 + 反例 |
| 性能基准（benchmark） | token / 延迟 / 步数三列 |

最贴切的是 OJ：**你在洛谷不会只交一份代码就完事，你会看它过了几个点、错在哪类点。**
W7 就是把"点"从代码换成了对话。

---

## 10. 验收怎么读

- `report_baseline.md` 与 `report_after_*.md` 两份都在，且能并排看出差异
- 能指着报告说出那句计划里的话（掉了几条、掉在哪类、成本降多少、你选什么）
- 至少一条断言是**因为轨迹错**而红，而不只是答案错
- 你能说出这次评测**测不到**什么（这是最容易被跳过的一问）

最后一条的意思是：20 条覆盖不了长尾。你能说清"我这 20 条测的是哪一类问题、
不覆盖哪一类"，比多跑 50 条更有价值。
