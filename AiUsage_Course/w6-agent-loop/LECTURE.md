# W6 讲义 · 手写那个循环

> 配合 `w6-agent-loop/` 使用。先读这份，再跑 `src/agent.py --fixture good_run.json`，
> 然后跑 `--fixture loop_trap.json` 看它翻车。**这一周不许用任何 agent 框架。**

---

## 0. 一句话

```python
while not done and steps < MAX:
    resp = llm(messages, tools)
    if resp.tool_calls:
        执行 → 结果 append 进 messages
    else:
        done
```

就这么多。你觉得"这也叫 agent？"——对，就叫。**框架替你做的就是这五行，外加一堆
你没要求过的抽象。** 真正难的地方不在循环，在三个配套问题：什么时候停、状态放哪、错了怎么不越错越远。

---

## 1. 为什么它看起来太简单

因为你在 W1–W5 已经把每个零件都摸过了：

| 零件 | 你在哪见过 |
|---|---|
| `messages` 数组怎么长 | W1（无状态，每轮重发） |
| `tools` 怎么定义 | W4/W5（description + schema） |
| `tool_calls` 怎么回填 | W4（`role: tool` + `tool_call_id`） |
| 上下文多贵 | W3（46k vs 600，同一批问题） |
| 工具错误怎么可读 | W5（`error` + `hint`） |

循环只是把它们串起来。**所以这周的功夫不在"让 agent 跑起来"，在"让它停得下来、错得明白"。**

---

## 2. 三个终止条件，缺一个都会出事

| 条件 | 缺了会怎样 | 你已经见过的证据 |
|---|---|---|
| 模型说完了（`tool_calls` 为空） | 永远不知道结束 | —— |
| 步数上限 | 跑到天亮，账单爆炸 | `loop_trap` 跑满 12 步 |
| token 预算 | 单步很贵时，步数内也会超支 | **`agent.py` 现在就是这样**：22,560 > 20,000，但它跑完了才停 |

`skeleton` 里 `TOKEN_BUDGET = 20_000` 定义了却没人用 —— 这不是我忘了，
是让你先看到后果，再补上。**你刚跑出来的那个"超预算 2560"就是最好的教材。**

还有一条容易被忽略：**退出原因要能区分**。

```python
return {"reason": "max_steps"}          # 差：说不清为什么停
return {"reason": "budget_exceeded",    # 好：能直接进 trace、进评测、进告警
        "spent": 22560, "limit": 20000,
        "last_tool": "search_notes"}
```

因为 W7 要断言"该停的时候停了没有"，而"停"和"停对"是两件事。

---

## 3. 状态外置：为什么不能靠 messages

现在你的计划、做到哪一步、得到了什么结论，全都隐式躺在 `messages` 里。
三个后果：

1. **不可中断**：跑到第 8 步崩了，你只能从头再来（因为历史没落盘）
2. **不可调试**：出问题时你面对的是 30 条消息，得自己还原"它当时想干嘛"
3. **不可评测**：W7 想问"该调的调了没有"，你得从对话里猜

所以状态要外置成结构化的东西：

```python
state = {
    "goal": "把 6.2 节转成 3 道复习题",
    "plan": ["定位小节", "提取公式", "出题", "自查"],
    "done": ["定位小节"],
    "facts": {"section": "week3.md:34-83", "formulas": ["...", "..."]},
    "budget": {"spent": 0, "limit": 20000},
}
```

它不是给你看的，是给**下一步的你**和**评测器**看的。W7 的轨迹断言直接读它。

## 4. 子 agent 的真正价值：上下文隔离

不是"分工"，不是"并行加速"，是**隔离**。

一个要读 30 个文件才能得出"第 3 章有两处断链"的子任务，如果放在主上下文里做，
那 30 个文件会把主上下文塞满、把成本拉高、把注意力冲散。丢给子 agent，它烧完自己的
上下文，只回一句结论——**主上下文干干净净**。

判据（W8 还会再用一次）：

> 过程脏、结论干净、且你不需要盯着过程 → 拆出去。
> 过程本身就是结论的一部分 → 别拆。

计划里建议本周**不写**子 agent（反模式 4：单 agent 评测过 80% 再谈拆分）。
理解这个概念就够了，动手留到八周之后。

## 5. ReAct 的脆弱点：错误会累积

第 1 步搜错了小节 → 第 2 步基于错误小节出题 → 第 3 步自查时发现"和笔记不一致"，
但它会倾向于相信自己前面写的东西 → 第 4 步交付一份自洽但错的答案。

缓解不是"写更长的 prompt"，是三件事：

1. **每步可验证**：工具返回里带 `file:行号`，下一步能核对
2. **结构化状态**：错的结论在 `facts` 里能被单独覆盖，而不是埋在对话里
3. **可回滚**：发现第 2 步错了，能回到第 1 步的 state 重来

这三条本周都要在 `state.py` 或 `agent.py` 里落一个最小版本。

## 6. 工具结果裁剪（TODO 2 的由来）

现在 `agent.py` 把工具返回值原样 append 回 messages。跑 `good_run` 时你没感觉，
跑 10 步的 `loop_trap` 时，每步都塞进 3 条命中 → 上下文线性膨胀 → 每步更贵 → 更快超预算。

这正是 W3 说的"第一成本杀手"。改法不是"少返回"，是**返回摘要 + 定位**：

```python
{"hits": [{"file": "week2.md", "start_line": 146, "end_line": 204, "snippet": "…"}]}
```

注意 snippet 已经是截断的（240 字）。如果你还想更省，就只回 `file/行号/标题`，
让模型自己决定要不要 `read_section`。**但别太狠**：只回行号不给任何内容，
模型会退化成"每次都要读"，反而更贵。这条线得你自己试。

## 7. 和你已有能力的对照

| 你已经会的 | W6 里的对应物 |
|---|---|
| 状态机（显式状态 + 转移条件） | `state` dict + 三种终止条件 |
| watchdog / 超时 / 重试上限 | `max_steps` + `token_budget` |
| ROS 2 action 的 feedback | `trace`：每步一行，可回放 |
| 分布式系统的"部分失败" | 工具返回 `error` 后模型自我修正 |
| 日志与黑匣子 | trace 落盘，出问题先看它而不是重跑 |

第三行最贴切：**action 的 feedback 不是给你调试用的，是给上层做决策用的**。
trace 也一样——W7 拿它做断言，不是拿它做展示。

## 8. 验收怎么做

计划里那道题是"读一章 → 找 2 个核心公式 → 出 3 道题 → 自查 → 输出 markdown"，带预算。
但真正能证明你写对了的是**反例**：

```
问："找第 99 章的内容。"
期望：在有限步内停下，明确说"没有第 99 章"（或"材料未覆盖"），
      并且 trace 里能看到它查过 list_chapters / search_notes 各几次。
不期望：12 步空转、或者编出一章内容、或者超预算才停。
```

这个实验比成功案例值钱：**它同时检验终止逻辑、错误处理、和"不编造"的边界。**

---

## 9. 一句话总结

- 循环五行，谁都会写
- **终止条件**决定它会不会烧钱
- **状态外置**决定它能不能被调试和评测
- **裁剪**决定它跑十步之后还认不认得清目标

三样都做到，你才不需要框架。做不到，框架也救不了你。
