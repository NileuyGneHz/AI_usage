# ADAPT · 给接手这个计划的 agent 的适配协议

> 这份文件不是给人学知识的，是给**下一个 AI 会话**用的：它读完就能知道
> "这个人现在在哪、该把哪一周调厚、哪一周压薄、哪些不能动"。
>
> 人类读者也可以看，但可以直接跳到第 4 节的旋钮表。

---

## 1. 先读什么（顺序不能反）

| 顺序 | 文件 | 你要从中得到什么 |
|---|---|---|
| 1 | `STATUS.md` | 进度到哪、哪些决策还没定 |
| 2 | 本周 `NOTES.md` | 他实际做了什么、踩了什么坑、**待定决策最后选了啥** |
| 3 | 上周 `NOTES.md` | 上周的坑有没有带过来（很多坑会跨周） |
| 4 | 本周 `BRIEF.md` 的「待定决策」 | 哪些旋钮还没拧，别替他决定 |
| 5 | 本周 `runs/`、`trace/`、`report*.md` | **数据**。日志比自述可信 |

第 5 条最重要：**永远先看数据，再听描述。** 一个人说"跑通了"，
和 `runs/*.jsonl` 里有 10 条记录，是两件事。

## 2. 三类信号，三种动作

### 信号 A：卡住了（时间在走，产出没有）

证据：`NOTES.md` 说"卡了两天"、`runs/` 三天没新增、某个实验反复出现同一个错误。

**动作**（按顺序试，别一次全上）：

1. **降级不跳过**：把当周任务砍到最小可验证版本。例：W3 只做 A vs B 两套策略。
2. **换零成本通道**：真模型跑不动 → mock 先验管线（但要标注"这组数字不能评质量"）。
3. **拆一步**：把"写 runner + 写 v3 + 跑对比"拆成"先写 runner 跑 v1 一例"。
4. **回补前置**：卡在 W4 的报文，通常是因为 W0 的 `raw_rpc.py` 没真看懂。
   回去重跑一次，10 分钟，比在 W4 挣扎两小时划算。

### 信号 B：跑得太快（数据太漂亮）

证据：W2 一次就 10/10、W5 一次就 10/10、W7 全绿。

**动作**：

1. **查假绿**：`must_include` 是不是空的？判分器是不是只判了 JSON 合法性？
2. **加难度**：换没见过的章节、加多步任务、加"材料未覆盖"的负例。
3. **换小模型**：如果小模型也全过，说明任务太简单，这一周的信息量不足。

> 太漂亮的数据通常意味着测试太弱，不是能力太强。

### 信号 C：方向偏了（做了很多，但不是这周该做的）

证据：W2 在调 temperature、W4 在写业务逻辑、W5 在改代码、W6 在选框架。

**动作**：对照 `LECTURE.md` 最后那节"验收怎么读"，逐条问"这条做到了吗"。
做不到的，就是偏了的方向。

| 周 | 典型跑偏 | 一句话纠正 |
|---|---|---|
| W2 | 在调措辞求"质量" | 先让格式 10/10，质量是下一步 |
| W3 | 在搭 RAG | 这周只算账，不做检索系统 |
| W4 | 在写业务逻辑 | server 只做协议适配，逻辑放 `notes_index.py` |
| W5 | 在改代码 | 改 description 和 schema，不是改实现 |
| W6 | 在挑框架 | 不许用框架 |
| W7 | 在写测试框架 | 20 条 + 三层断言就够 |
| W8 | 在重写别人的 skill | 先读（L1），再写（L2），最后才改（L3） |

## 3. 不可砍清单（改计划前先看这个）

1. **W3 不能跳** —— 后面所有成本与稳定性的依据
2. **W5 的「真实 client 实测 10 问」不能砍** —— 唯一能验证 description 好坏
3. **W6 的「找第 99 章」优雅失败实验不能砍** —— 唯一能证明终止逻辑正确
4. **W7 的「改一处前后对比」不能砍** —— 唯一一次把优化变成可验证动作
5. **W8 的 L3 不能砍** —— 唯一能证明"能安全修改不完全理解的文件"

砍掉任意一条，那一周的产出就只剩"我做过了"。

## 4. 每周旋钮表（可调什么、调了会牵动谁）

| 周 | 旋钮 | 位置 | 调大/调小的后果 | 牵动 |
|---|---|---|---|---|
| W2 | case 数量 | `cases.jsonl` | 少 → 快但看不出趋势；多 → 贵 | W7 的 evalset 来源 |
| W2 | 是否拆 v3a/v3b | `prompts/` | 拆 → 可归因；不拆 → 快 | W7 单变量习惯 |
| W3 | `--scope` | `run_compare.py` | subset 快；all 会撞窗口 | W4 的返回裁剪规格 |
| W3 | `k` | `--k` | 大 → 召回好但贵 | W4 `search_notes` 的 k 默认值 |
| W3 | 压缩预算 | `c_compress.MAX_CHARS` | 小 → 便宜但丢限定 | W5 上下文增量 |
| W4 | tool 粒度 | `tools.spec.md` | 3 个够用；合并会误调用 | W5 的 10 问准确率 |
| W4 | 是否做 HTTP | — | 跳过最省时，且不影响其他周 | 无 |
| W5 | 10 问的来源 | `questions.md` | 真实提问 → 测得准；现编 → 偏袒实现 | W7 evalset |
| W6 | `max_steps` / `TOKEN_BUDGET` | `agent.py` | 小 → 容易优雅失败；大 → 更贵 | W7 的 max_steps 断言 |
| W6 | 裁剪力度 | `compact()` | 狠 → 省但模型反复读；软 → 贵 | W7 平均 token |
| W7 | evalset 条数 | `evalset.jsonl` | 20 是下限；<10 结论不可靠 | 全部后续对比 |
| W7 | 是否上 judge | `run_eval.py` | 上 → 省人力但要先校准 | — |
| W8 | L2 选题 | `skill-src/` | 选天天做的 → 有素材；选炫的 → 写不出来 | — |

**改任何一个旋钮，只改一个，然后重跑当周的数据。** 这是全计划唯一的实验纪律。

## 5. 调整后怎么写回去

每次调整都要留痕，否则下一次会话会重复踩坑。三处：

1. **当周 `NOTES.md`** 最后一节「待定决策的最终选择」：选了什么、和原计划差在哪、为什么
2. **`STATUS.md`** 的进度表：状态改成「进行中 / 完成 / 降级完成」
3. **`runs/` 或 `report*.md`**：数据落盘，别只留在对话里

格式建议：

```markdown
### 2026-11-05 调整
- 信号：W3 卡了两天（A 全量超窗口）
- 动作：降级为 subset（5 章），全量只做 dry-run 估算
- 数据：subset 下 A=46k token，B=2.9k，C=0.6k
- 放弃的：拐点实验的实测部分，只保留估算
- 影响：W4 的 search_notes 按 subset 规模定 k=3
```

## 6. 给 agent 的三条硬规则

1. **不要替他做判断类作业**：v3 的负例、`must_include`、归因、结论 —— 这些是本周的产出。
   你帮他写完，这周就消失了。
2. **可以替他做管道类工作**：跑脚本、修 import、生成骨架、整理表格、解释报错。
3. **改代码前先读 `NOTES.md`**：他可能在上一轮已经试过你要改的那条路，并且记下了为什么不行。

第 1 条与第 3 条同样重要：**你要保住的是"他做过"，不是"代码能跑"。**
