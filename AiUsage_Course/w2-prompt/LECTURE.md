# W2 讲义 · 把 prompt 写成接口

> 配合 `w2-prompt/` 使用。先读这份，再跑 `run.py --dry-run`，最后才花 token。
> 本周没有新概念，只有一个视角切换：**你写的是函数签名，不是文章。**

---

## 0. 一句话

W1 你已经看到：请求体里就是一个 `messages` 数组，模型读完给你一段字符串。

W2 要解决的是这段字符串**不可信**的问题。不可信不是"它会说错话"，而是
**它可能不是一个能被程序消费的东西**。把这件事变成可测量的，就是本周全部内容。

---

## 1. 三种失败，三种修法

大多数人调 prompt 失败，是因为把三种完全不同的失败混成一句"效果不好"。

| 失败类型 | 长什么样 | 该改哪里 |
|---|---|---|
| **格式失败** | 前后带解释、外面裹 ` ```json `、根本不是 JSON | 输出契约（schema / 指令位置） |
| **结构失败** | 是 JSON，但字段名错、数量不对、多包一层 `{"data": …}`、枚举写了中文 | 输出契约（字段清单 + 负例） |
| **语义失败** | 结构全对，但内容是编的、答案抄了题干、考的不是这一节 | 输入边界（"只用笔记里的内容"）+ 语料切分 |

三种失败的**频率差一个数量级**：真实项目里格式与结构失败占九成，语义失败占一成，
但你花在语义上的注意力往往占九成。先把前两类清零，再谈质量。

`run.py` 的判分器就是这个分类器的实现：`bad_json` / `bad_schema` / `ok` / `insufficient`，
四类互斥，出报告时按类计数，不给你一个含糊的"通过率 60%"。

## 2. 五个槽位，对应函数的四件套

| 槽位 | 对应 C++ 里的什么 | 作用 |
|---|---|---|
| 角色 | 类名 / 命名空间 | 只定语气与词汇，**不提升正确率** |
| 任务 | 函数名 + 一行注释 | 说清"做什么"，一句话 |
| 输入边界 | 参数的前置条件 + 断言 | 限定材料范围，禁止外部知识 |
| 输出契约 | 返回类型 + 结构体定义 | 字段、类型、数量、枚举，全部写死 |
| 失败处理 | 抛异常 / 返回错误码 | 信息不足时输出 `insufficient`，**不许猜** |

`prompts/v2.txt` 就是这五段的骨架。你现在能看懂它为什么这么排版：它不是散文，
它是**分节的契约**，每一节都能被单独改、单独测。

v1 → v2 的差别是"从口头需求到 .h 声明"。v2 → v3 的差别是"从 .h 声明到编译器检查"：
字段清单从正文搬进 JSON Schema，由服务端或校验器来拦。

## 3. 指令优先级，和一条安全边界

```
system  >  developer  >  user  >  tool 返回
```

两条推论，本周都会用到：

1. **同一条硬约束，放在越靠后越容易被遵守**（近因）。把"只输出 JSON"只写在很长的
   system 开头，效果通常不如在 user 末尾再强调一次。这不是玄学，是位置效应，值得你
   用 `--dry-run` 看一眼渲染后的顺序。
2. **tool 返回是不可信输入**。它长得像文本，但它只是数据，不是指令。W5 会实战注入，
   现在先记住这条边界：**任何来自工具的内容，都不能被当作用户指令执行**。

---

## 4. few-shot 定格式，负例省 token

- few-shot 的边际收益在下降，但它钉"什么算合格答案"仍然有效——**定格式与边界，不教能力**。
- 一条负例往往比三个正例便宜：`不要用 ```json 包裹` 一句话抵得上三份完整示例。
- 但负例超过 4 条会开始抢注意力，变成"负面清单"淹没任务。2–4 条，且每条只针对
  你在数据里**真的见过**的失败形态。

`prompts/v3.template.txt` 的「负例」一节留了一个空位，写什么由你定——但必须来自
W1 实验里你亲眼见过的那个失败，而不是网上抄来的清单。

## 5. schema 到底约束了什么（以及它约束不了什么）

| 层 | 谁在拦 | 拦住什么 | 拦不住什么 |
|---|---|---|---|
| 服务端 `response_format: json_schema` | 模型侧解码约束 | 语法、字段、枚举、数量 | 内容对不对 |
| 服务端 `response_format: json_object` | 模型侧 | 只保证是合法 JSON | 字段、数量、枚举 |
| 客户端 `schema_check.py` | 你的代码 | 上面全部结构规则 | 内容对不对 |

**关键认识**：schema 的价值不是"让模型更聪明"，是**把失败从"悄悄错"变成"显式报错"**。
没有它，模型给你一张字段名叫 `题目` 的卡片，你的程序在三天后崩在别处。

还有一件容易被忽略的事：**strict schema 和"拒答"是打架的**。如果 schema 只允许
`{"cards": [...]}`，那"信息不足"这个合法结果就没地方放。所以
`schema/cards.schema.json` 用 `oneOf` 给了两条合法出路。这是真实项目里必须做的一个决定。

`run.py --format auto` 还演示了降级：先试 `json_schema`，服务商 400 就退回
`json_object`，并在报告里标 `(降级)`。W1 讲义里"服务商不支持时报错，代码里要能降级"
那句话，在这里落地。

## 6. 你已经有这个思维：洛谷

你在洛谷交过同一道题的三份写法，跑同一批测试点，看哪份过得多。

| 洛谷 | W2 |
|---|---|
| 三份代码 | v1 / v2 / v3 三版 prompt |
| 测试点 | `cases.jsonl` 的 10 条固定输入 |
| OJ 判对错 | `schema_check.py` 判格式与结构 + 你判内容可用 |
| 提交记录 | `runs/<时间戳>.jsonl` |

**唯一的区别**是 OJ 能自动判对错，而"内容可用率"这一列必须人判。这就是为什么本周
的工作量不在写代码，在**定标准 + 判 10 条**。

## 7. 度量与纪律

四个数，缺一个都不能下结论：

| 指标 | 怎么来 | 说明 |
|---|---|---|
| 格式合规率 | 判分器 | 目标 10/10 |
| 内容可用率 | **人判** 10 条（完全可用 / 部分 / 不可用） | 别急着上 LLM-as-judge，W7 才校准 |
| 平均 token | `usage` | 验收线：v3 ≤ v1 的 1.5 倍 |
| 平均延迟 | 客户端计时 | 只作参考，网络抖动大 |

三条纪律，破了就白做：

1. **同一组 cases、同一模型、同一温度**。改任意一项，三版之间就不可比。
2. **每版至少跑 3 次**（`--repeat 3`）。W1 实验 2 已经证明 temperature=0 也不保证逐字相同。
3. **一次只改一个变量**。v3 同时加了 schema 和负例，所以验收时你没法归因。有余力就拆
   成 v3a / v3b 各跑一遍——这就是 W7 单变量回归的预演。

---

## 8. 四个常见误解

1. **"你是资深机器学习专家"能提升正确率。** 不。它改语气，不改事实。改正确率的是
   输入边界的精确度与失败处理。
2. **"请一步步思考"是万灵药。** 对多步推理题有一点用，对格式题完全没用，还会让输出变长。
3. **token 越少越好。** 不。v3 会比 v1 贵，因为 schema 本身就是 token。验收线允许 1.5 倍，
   买的是确定性——这笔交易通常是划算的，但你要知道自己在付钱。
4. **通过率 100% 就说明 prompt 好。** 10 条 cases 全过只说明"这 10 条能过"。真正的检验
   是换一批没见过的章节，或者让同学拿他的笔记试。

---

## 9. 验收怎么读

- v3 合规 **10/10**，且总 token **≤ v1 的 1.5 倍**
- 你能指着失败明细说：这条是格式失败还是结构失败，修法在哪一槽
- 你能回答：如果把负例全删掉，哪几条会退回去？——答不出来说明你没做消融，只做了叠加

过关之后再进 W3。W3 会把你刚建立的一切搬到一个新问题上：**这么多 token，到底该塞什么进去。**
