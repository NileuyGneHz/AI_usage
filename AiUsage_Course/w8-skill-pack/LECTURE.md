## 1. 为什么"现在能用"不等于"对"

那批文件现在确实能用。原因是：**写它们的那一刻，模型和环境是对的。**

但你没有能力回答下面任何一问：

- 里面那条 `ros2 topic hz /scan` 现在的消息类型还叫这个吗？
- 那个 `/home/xxx/rm_ws/...` 路径还在吗？
- 第 3 步"等 5 秒"在现在这台机器上够吗？
- 如果它执行错了，是这一百多行里的哪一句导致的？

W0 你已经撞过一次版本墙（`FastMCP` → `MCPServer`）。那次你花 10 分钟就定位了，
因为错误**当场报出来**。而 skill 的坑是**沉默**的：它照着一句过期指令执行，你不看输出
就永远不知道。

**本周要补的就是这个：给"沉默的错误"装上断言点。**

## 2. 三选一判据（这一周要真正会用）

| 形态 | 什么时候用 | 你的例子 |
|---|---|---|
| **tool / MCP** | 确定性、需权限、要被模型主动调用 | `search_notes`、编译检查 |
| **skill** | 多步流程知识、判断规则、踩坑经验 | `bt4-loop-decorator-pitfalls` |
| **subagent** | 需要独立上下文、过程脏但结论干净 | "扫 30 个文件找断链" |

一句话：**能写成代码的写代码，只能写成判断的写手册，会污染主上下文的拆出去。**

判据的推导过程在根 `README.md` 附录一（两条调用链路）。你现在应该能不看书复述：
skill 回填的是文字指令（有概率偏差），tool 回填的是函数返回值（确定性）。

## 3. 渐进披露：三层，各管一件事

```
frontmatter  name + description   →  常驻，决定「想不想得起来用」= 召回率
SKILL.md 正文                     →  命中才加载，决定「会不会做」
references/ + scripts/            →  正文点名才读，决定「做得稳不稳」
```

三个推论：

1. **description 决定召回**，写症状不写功能。这条在 W0 练过，W5 又用 tool description
   练了一次——**它和 MCP 的 tool description 是同一个技能**。
2. **正文超过 120 行就要怀疑**。不是风格问题，是"命中后一次性灌进上下文"的成本问题。
3. **scripts 决定可靠性**：模型执行 10 行固定命令的可靠性，永远低于执行 1 个脚本。
   这不是对模型的不信任，是对"每一步都可能被读错一个字"的工程回应。

## 4. 怎么判断一个 skill 过期了（本周的核心方法）

不要凭感觉。给每条可疑指令找一个**可执行的断言点**：

| 可疑的东西 | 断言点 | 断了会怎样 |
|---|---|---|
| 文件/目录路径 | `test -d <path>` / `ls` | 立刻知道，不用等它跑一半 |
| 命令是否存在 | `command -v <cmd>` | 同上 |
| 版本要求 | `<cmd> --version \| grep` | 版本墙（W0 那种） |
| 输出格式 | 抓一行样例，用 `grep` 断言字段名 | 模型读到不认识的字段会瞎猜 |
| 服务/端口 | `ss -ltn \| grep :8000` | "连接被拒"被误读成"服务没启动" |

**这才是 L1 第五问"若执行错了，能定位到是哪一句"的答案**：能定位，是因为每一句都有断言点，
而不是因为文件写得整齐。

推论：**能被断言的部分，就该变成 scripts/。** 剩下的才是真正的"判断"，那部分留给人读。

## 5. 接管三步，顺序不能反

### L1 · 读（2h）

拿最短的和最长的两个极端样本对照读。为什么取极端：60 行的和 371 行的，
它们的失败方式完全不同——短的是"信息不足"，长的是"信息过载"。

五问（模板在 `review.template.md`）里，真正难的是第 4、5 问：

- 第 4 问考的是**你怎么知道它过期了**（第 4 节的方法）
- 第 5 问考的是**可定位性**（有没有断言点）

### L2 · 写（4h）

选题标准：**你每周都在做、步骤 ≥5、每次都得想一下顺序**的事。
写的时候用 `skill-src/SKILL.template.md`，写完跑 `lint_skill.py`。

硬指标：正文 ≤120 行、≥1 个脚本、description 按症状写。然后 5 个场景测命中率。

### L3 · 改（2h）

挑一个 AI 写的 skill，**只改一个变量**：

- 只改 `description`，或
- 只把长案例拆进 `references/`

改完同样 5 个场景复测。这一步的目的不是"改好"，是**证明你能安全地修改一个你并不完全
理解的文件**——这是接管的核心能力，也是本周唯一无法用"我写了一个新 skill"替代的证据。

## 6. 和你已有能力的对照

| 你已经会的 | W8 里的对应物 |
|---|---|
| runbook / on-call 手册 | SKILL.md：步骤 + 判断 + 例外 |
| 把 runbook 脚本化 | scripts/：确定性步骤抽出来 |
| 配置管理（幂等、可回滚） | L3 的单变量改动 + 前后对比 |
| code review（读懂别人的意图） | L1 的五问：读的是设计，不是内容 |
| 版本兼容性判断 | 第 4 节的断言点 |

第四行最贴切：**code review 时你不是在挑语法，你是在判断"作者当时想解决什么、
这个解法现在还成立吗"**。L1 的五问就是同一个动作，只是对象从代码变成了手册。

---

## 7. 验收怎么读

- L1：五问每条都有**具体证据**（行号/原句），不接受"看起来还行"
- L2：`lint_skill.py` 通过 + 5 个场景命中 ≥4/5 + 至少 2 个"不该命中"的场景没误触发
- L3：改动前后数据都在，且**能指出差异来自哪一句**
- 加分：同学按 README 20 分钟跑通，不需要你在旁边解释

第 3 条是全部八周的收敛点：**能指出差异来自哪一句**，意味着你既理解了这个文件，
又能控制自己的改动。这就是从"使用者"变成"设计者"的标志。
